What happens when you open an HTTPS URL

Networking · concept explainer · one example clock, stated under the diagram · www.example.com is a placeholder

Before the first byte of the page arrives, the browser does three things, each waiting for an answer: it looks up the server's numeric address (DNS), opens a connection to it (TCP) and sets up encryption with it (TLS). Only then does it send the request. If the nearby CDN server, a copy server the site rents close to you, doesn't have the page, it fetches it from the site's own server far away. Almost all the waiting is round trips, not data. In our example clock the first visit takes 180 ms to the first byte; a repeat visit takes 40 ms, because most of those round trips are skipped.

Round trips, not bandwidthEach step sends a message and waits for the reply. Distance sets the cost, so a server 10 ms away beats a faster one 100 ms away.
The first visit pays for everything180 ms here. On a repeat visit the address, the encryption keys and the page are already remembered: 40 ms.
The nearby server does the heavy liftingThe handshakes happen with a CDN server close to you. It only talks to the far-away origin when it lacks the page.

  1. 1 · DNS lookup: find the address

    The browser only knows the name www.example.com. It asks a DNS resolver, the lookup service your network gives you (usually your internet provider's), for the server's numeric address. This resolver doesn't have the answer stored, so it asks the servers in charge of that name. 40 ms in all.

    The answer comes with a TTL of 300 s: the resolver, the operating system and the browser may reuse it that long without asking again. For a site behind a CDN, the address it returns belongs to a CDN server near you, not to the origin.

    What travelsquery: www.example.com A ? answer: www.example.com. 300 IN A 203.0.113.10

  2. 2 · TCP handshake: open a connection

    The browser opens a connection to that address with three short messages: "can we talk?" (SYN), "yes" (SYN-ACK) and "OK" (ACK). The first two cost one round trip to the CDN server: 20 ms.

    The SYN/ACK exchange makes both sides agree on starting sequence numbers. The final ACK doesn't wait for anything: the browser sends it together with the first encryption message. Every round trip here is one RTT to the CDN edge, not to the origin.

    What travelsSYN seq=x SYN-ACK seq=y ack=x+1 ACK ack=y+1 (sent with the ClientHello)

  3. 3 · TLS handshake: agree on encryption

    Before anything private is sent, the browser and the server agree on secret keys, and the server proves it really is www.example.com by showing its certificate, an identity card signed by an authority the browser trusts. With TLS 1.3 this costs one more round trip: 20 ms.

    In the TLS handshake, the ClientHello names the site in SNI, so one address can serve many sites, and offers HTTP/2 through ALPN. The server answers with ServerHello and its key share; everything after that is already encrypted: the ALPN choice (h2), the certificate chain, a signature proving it holds the certificate's key, and Finished.

    What travelsClientHello: TLS 1.3 · key share (X25519) · SNI www.example.com · ALPN [h2, http/1.1] ServerHello: key share encrypted → EncryptedExtensions (ALPN h2) · Certificate (leaf + intermediate) · CertificateVerify · Finished

    Yes, the site's name, though not the page. The SNI in the ClientHello travels unencrypted (unless both sides use Encrypted Client Hello), and so does a classic DNS query. The path (/cart), the headers and the page itself are encrypted.

  4. 4 · The request: "GET /"

    The browser sends its last encryption message (Finished) and, in the same burst, the actual request for the page: "GET /". It reaches the CDN server 10 ms later, at 90 ms.

    Because ALPN picked HTTP/2, the request is a HEADERS frame on stream 1 of the encrypted connection. The page's CSS, scripts and images will later travel over this same connection as new streams, side by side.

    What travelsHEADERS stream=1 :method GET :scheme https :authority www.example.com :path / accept text/html accept-encoding gzip, br

  5. 5 · Cache miss: the CDN server asks the origin

    The CDN server near you doesn't have this page yet, so it asks the site's own server, the origin, which is farther away: 80 ms there and back. This is the longest wait of the whole trip.

    The CDN edge ended your encrypted connection itself and has its own connection to the origin. Here that connection is already open, so the miss costs exactly one edge↔origin round trip.

    If that connection were cold, the edge would first pay its own TCP and TLS handshakes, 80 ms each: 240 ms instead of 80, and 340 ms to the first byte instead of 180. Keeping warm, reused connections to the origin is a large part of what a CDN does for you on a miss.

    What travelsedge → origin: GET / (over a connection kept open from earlier requests) origin → edge: 200 OK cache-control: public, max-age=300

  6. 6 · Response: the page arrives

    The CDN server passes the page on to the browser and keeps a copy for the next visitor. The first byte reaches the browser at 180 ms; the browser starts reading the page right away.

    The edge keeps the copy for as long as the origin's cache-control allows (300 s here). The next visitor served by that edge gets a cache hit and skips step 5 entirely.

    What travelsHEADERS stream=1 :status 200 content-type text/html DATA stream=1 <!doctype html>…

  7. 7 · Keep-alive: the connection stays open

    The browser doesn't hang up. The page's images and scripts, and your next click on the same site, travel over this open connection without repeating steps 1 to 3: each new request costs one round trip, 20 ms.

    This is keep-alive. After the handshake the server also sent a session ticket (NewSessionTicket), which lets a later visit resume encryption with 0-RTT: the request rides along with the ClientHello.

    DNS: no, if the cached answer's TTL hasn't run out. TCP: yes, one round trip. TLS: no extra round trip, because the GET travels with the ClientHello (0-RTT). Origin: no, if the CDN server still has the page. 40 ms instead of 180.

Common mistakes

  • "HTTPS is slow because encryption is heavy." The math takes a few milliseconds of CPU. The cost is the extra round trip of the TLS handshake. Fix: TLS 1.3, a CDN close to users, and connections that stay open.
  • "0-RTT means no round trips." It removes the TLS round trip only. Over TCP the connection handshake still costs one, and the answer still needs the request to cross. Only HTTP/3 over QUIC folds the connection and encryption handshakes together.
  • "A DNS change takes effect at once." Resolvers and browsers keep the old answer until its TTL runs out. Lower the TTL a day before moving a site, then raise it again.
  • "HTTPS hides which site I visit." It hides the page, not the name: the SNI and a classic DNS query show www.example.com, unless Encrypted Client Hello and encrypted DNS are in use.
  • "The server sends its whole certificate chain, root included." It sends its own certificate and the intermediates; the root is already in the browser. Forgetting an intermediate works in one browser and fails in another.
  • "The CDN asks the origin every time." Only on a miss, and cache-control decides what counts as one. A page marked private or no-store goes to the origin on every request.

Where you'll meet it

  • Your browser's developer tools. The Network tab's Timing view splits each request into DNS lookup, initial connection, SSL and waiting for the server response, the same phases as the diagram.
  • curl. curl -so /dev/null -w '%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer}\n' prints the clock at the end of DNS, TCP, TLS and the first byte.
  • dig. dig www.example.com shows the answer and its remaining TTL; run it twice and watch the number go down.
  • openssl. openssl s_client -connect www.example.com:443 -servername www.example.com -alpn h2 shows the SNI you sent, the certificate chain the server returned and the ALPN it picked.
  • A CDN dashboard. The cache hit ratio is the share of requests that skip step 5; the origin latency is the 80 ms leg.

The fine print

  • 0-RTT data can be replayed. The early request is encrypted with keys from the earlier session ticket, before the server has said anything in this connection, so an attacker who records it can send it again. Servers and CDNs therefore accept early data only for safe, idempotent requests such as a plain GET, never for a payment or a form post. A CDN can forward the request to the origin with an Early-Data: 1 header, and the origin can answer 425 Too Early to make the browser retry after the full handshake.
  • When 0-RTT doesn't happen, because the ticket expired, the request isn't idempotent or the server declines early data, resumption still skips the certificate but costs the TLS round trip: the repeat visit becomes 60 ms instead of 40.
  • The edge's connection to the origin. The 80 ms miss assumes the edge already had a warm, reused connection to the origin. A cold one adds a TCP and a TLS handshake at 80 ms each: the miss becomes 240 ms and the first visit 340 ms. CDNs keep connection pools and often add a shield tier, a single cache close to the origin, so most misses never reach it.
  • HTTP/3 over QUIC. The connection and encryption handshakes share one round trip, so the first visit would be 160 ms. A repeat visit with 0-RTT sends the GET in the very first packet: 20 ms. The browser usually learns that a site speaks HTTP/3 from an earlier response (Alt-Svc) or from a DNS HTTPS record, so the very first visit is often HTTP/2.
  • TLS 1.2 needed two round trips for a full handshake, so the same first visit would take 200 ms.

The timings are a model, not a measurement: it leaves out server think time, TCP slow start, packet loss and the certificate check. Measure your own site with the tools above.

Glossary

RTT
Round-trip time: how long a message takes to reach the other side and its answer to come back. Here 20 ms between the browser and the CDN edge, 80 ms between the edge and the origin.
DNS resolver
The server that looks up names for your device, usually your internet provider's or a public one. It caches answers and asks the authoritative servers when it has none.
TTL
Time to live: how many seconds a DNS answer may be reused before asking again. 300 s in the example.
SYN/ACK
The flags of the TCP opening handshake: SYN asks to open a connection, SYN-ACK agrees, ACK confirms. One round trip before data can flow.
TLS handshake
The exchange that agrees on encryption keys and proves the server's identity. TLS 1.3 needs one round trip for a new connection; TLS 1.2 needed two.
SNI
Server Name Indication: the hostname the browser puts in the ClientHello, so one address can serve many sites, each with its own certificate. It travels unencrypted unless Encrypted Client Hello (ECH) is used.
ALPN
Application-Layer Protocol Negotiation: the browser lists the protocols it speaks (h2, http/1.1) in the ClientHello and the server picks one in its encrypted extensions.
Certificate chain
The server's own certificate plus the intermediate certificates that link it to a root authority the browser already trusts. The root itself is not sent.
CDN edge
A server of a content delivery network close to the user. It ends the encrypted connection, serves cached copies and forwards misses to the origin.
Origin
The site's own server, where the content really comes from. Often far from the user.
Keep-alive
Keeping a connection open after a response, so later requests skip the DNS, TCP and TLS steps. HTTP/2 also runs many requests over it at once.
0-RTT
TLS 1.3 early data: on a resumed session the browser sends the request together with the ClientHello, using a ticket from an earlier visit. It saves the TLS round trip, but the early data can be replayed, so only safe requests use it.
